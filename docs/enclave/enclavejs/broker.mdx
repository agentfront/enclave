# @enclave-vm/broker

Tool broker and session management for the EnclaveJS streaming runtime. It runs scripts in an `@enclave-vm/core` sandbox on your server, gives them the tools you register, and streams what happens as events, in process or over HTTP.

The broker does not authenticate callers, limit request rates or encrypt sessions. Put authentication in front of its routes, and tell the routes who the caller is (see [Who may see a session](#who-may-see-a-session)).

## Installation

```bash
npm install @enclave-vm/broker
```

## Quick Start

```typescript
import { createBroker } from '@enclave-vm/broker';
import { z } from 'zod';

const broker = createBroker({
  // Options of the sandbox go under `enclave`
  enclave: { securityLevel: 'SECURE' },
});

// Register a tool
broker.tool('fetchData', {
  description: 'Fetch a record by id',
  argsSchema: z.object({ id: z.string() }),
  handler: async ({ id }, { signal }) => {
    const response = await fetch(`https://api.example.com/data/${encodeURIComponent(id)}`, { signal });
    return response.json();
  },
});

// Execute code and wait for the result
const result = await broker.execute(
  `
  const data = await callTool('fetchData', { id: '42' });
  return data;
`,
  {
    onEvent: (event) => {
      if (event.type === 'tool_call') console.log('calling', event.payload.toolName);
    },
  },
);

if (result.success) {
  console.log(result.value);
} else {
  console.error(result.error);
}

await broker.dispose();
```

A script calls a tool with `callTool(name, args)`. `broker.execute()` resolves with the final result; the events of the run are handed to `onEvent`.

## Broker Configuration

```typescript
import { createBroker, type BrokerConfig } from '@enclave-vm/broker';

const config: BrokerConfig = {
  // Options of the sandbox (CreateEnclaveOptions of @enclave-vm/core)
  enclave: {
    securityLevel: 'SECURE', // 'STRICT' | 'SECURE' | 'STANDARD' | 'PERMISSIVE'
  },

  // Limits of every session (SessionLimits of @enclave-vm/types)
  limits: {
    maxToolCalls: 20,
    toolTimeoutMs: 10_000, // run time of the script
    perToolDeadlineMs: 5_000, // one tool call
    sessionTtlMs: 60_000,
  },

  // What a session keeps for a replay
  history: { maxEvents: 10_000, maxBytes: 4 * 1024 * 1024 },

  // The session registry
  sessions: {
    maxSessions: 100,
    cleanupIntervalMs: 60_000,
  },
};

const broker = createBroker(config);
```

<Warning>
`createBroker` reads `sessions`, `enclave`, `limits` and `history`. Any other key is ignored and reported with a warning. In particular, `securityLevel` at the top level has no effect: write `enclave: { securityLevel }`.
</Warning>

### Limits

| Limit | Default | What it bounds |
|-------|---------|----------------|
| `maxToolCalls` | 50 | Tool calls of one session |
| `toolTimeoutMs` | 30000 | The run time of the script (the sandbox timeout) |
| `perToolDeadlineMs` | 30000 | One tool call: the handler's `signal` is aborted. A tool's own `config.timeout` applies when it is lower |
| `deadlineMs` | 0 (none) | The whole session, counted from its creation |
| `sessionTtlMs` | 60000 | How long a session stays registered; a session past it is cancelled at the next cleanup |
| `maxToolResultBytes` | 5 MB | A tool result as serialized JSON; a larger one fails the call |
| `heartbeatIntervalMs` | 15000 | Interval of `heartbeat` events |
| `cancelOnFirstError` | false | Whether the first failed tool call cancels the session |

The limits of the broker bound every session. A session created in process can name its own value for a limit (the other limits keep the broker's values); a session created over HTTP can only lower `maxToolCalls` and its lifetime.

## Tools and Secrets

```typescript
import { z } from 'zod';

broker.secret('MAIL_API_KEY', process.env.MAIL_API_KEY!);

broker.tool('sendEmail', {
  description: 'Send an email to a recipient',
  argsSchema: z.object({
    to: z.string().email(),
    subject: z.string().max(100),
    body: z.string(),
  }),
  secrets: ['MAIL_API_KEY'],
  config: { timeout: 10_000 }, // this tool's own timeout
  handler: async (args, context) => {
    context.sessionId; // session the call belongs to
    context.callId; // id of this call
    context.secrets.MAIL_API_KEY; // the secrets the tool asked for
    context.signal; // aborted on timeout and when the session is cancelled

    await mail.send(args, { apiKey: context.secrets.MAIL_API_KEY, signal: context.signal });
    return { sent: true };
  },
});

broker.hasTool('sendEmail'); // true
broker.listTools(); // ['sendEmail']
broker.removeTool('sendEmail');
```

Arguments are validated against `argsSchema` before the handler runs. Secrets are handed to the handler only and are not part of any event. Tool arguments and the result of a script are part of the events: keep secrets out of them.

## Sessions

`broker.execute()` creates a session, runs the script and removes the session. To keep a session around, create it yourself:

```typescript
const session = broker.createSession({
  limits: { maxToolCalls: 5 }, // the other limits stay the broker's
});

const unsubscribe = session.onEvent((event) => {
  console.log(event.seq, event.type);
});

const result = await session.execute(`return await callTool('fetchData', { id: '42' });`);

session.state; // 'completed' | 'failed' | 'cancelled' | ...
session.getEvents(); // the kept events
await session.cancel('no longer needed'); // no effect on a finished session

broker.getSession(session.sessionId);
broker.listSessions();
await broker.terminateSession(session.sessionId);
```

A session id names one session: `createSession({ sessionId })` throws for an id that is in use, and when `sessions.maxSessions` sessions are registered. A finished session stays registered, so that it can be replayed, until the next cleanup.

### What a session keeps

A session keeps its most recent events for replays, up to `history.maxEvents` events and `history.maxBytes` bytes. When a bound is reached the oldest events are dropped; `session.firstReplayableSeq` is the lowest sequence number from which everything is still kept.

### Cancelling

A session runs in the broker's process, on its thread. Cancelling a session aborts the tool call in flight and refuses every later one. It does not interrupt a script that is computing: such a script holds the thread until it ends or reaches `toolTimeoutMs`.

<Warning>
One script that computes without calling a tool blocks every other session of the broker for up to `toolTimeoutMs`. Keep that limit low, and run the broker in a process of its own when you serve callers you do not trust.
</Warning>

## HTTP API

### Express Integration

```typescript
import express from 'express';
import { createBroker, createSessionHandler, registerExpressRoutes } from '@enclave-vm/broker';

const broker = createBroker();
const handler = createSessionHandler({
  broker,
  identify: (request) => (request.raw as { user?: { id: string } }).user?.id,
  allowedOrigins: ['https://app.example.com'],
});

const app = express();
app.use(express.json({ limit: '1mb' }));
app.use(authenticate); // your authentication middleware
registerExpressRoutes(app, handler);

app.listen(3000);
```

| Route | What it does |
|-------|--------------|
| `POST /sessions` | Creates a session, runs `code`, answers with the events as NDJSON until the `final` event |
| `GET /sessions` | Lists sessions |
| `GET /sessions/:sessionId` | State of one session |
| `GET /sessions/:sessionId/stream` | Replays the kept events from `?fromSeq=N` on and follows the session until it ends |
| `DELETE /sessions/:sessionId` | Ends a session |
| `POST /sessions/:sessionId/cancel` | Ends a session (the `cancelUrl` of the `session_init` event) |

To mount the routes under a prefix, register them on an Express router and mount the router:

```typescript
const router = express.Router();
registerExpressRoutes(router, handler);
app.use('/api/enclave', authenticate, router);
```

`createExpressRouter` is deprecated: it registers no route. For another framework, adapt its request and response to `BrokerRequest` and `BrokerResponse` and call the handlers of `handler.getRoutes()`.

### Who may see a session

<Warning>
Without an `identify` hook the routes do not tell callers apart. Whoever can reach them can list every session, read its state, replay its events (tool arguments and the final result included) and end it. Authentication in front of the routes does not change that: an authenticated caller still reaches the sessions of every other caller.
</Warning>

With `identify`, every session belongs to the caller that created it:

```typescript
const handler = createSessionHandler({
  broker,
  identify: (request) => {
    // request.raw: the framework's request; request.headers: its headers
    const user = (request.raw as { user?: { id: string } }).user;
    return user?.id; // a stable, non-empty string per caller, or nothing
  },
});
```

- `GET /sessions` lists the caller's own sessions.
- Reading, replaying and ending a session is answered only for its owner. Another caller gets `404`, the answer of an id that does not exist.
- A request for which the hook returns nothing, or throws, is answered with `401`.
- A session created in process has no owner and is not reachable over the routes, unless you create it with `owner`.

The hook identifies a caller; it does not verify a credential. Do that in your own middleware or inside the hook.

### Handler Options

```typescript
import { createSessionHandler, type SessionHandlerConfig } from '@enclave-vm/broker';

const config: SessionHandlerConfig = {
  broker,
  identify: (request) => undefined, // see above
  cors: true, // default
  allowedOrigins: ['https://app.example.com'], // default ['*']
  allowedHeaders: ['X-API-Key'], // besides Content-Type, Accept, Last-Event-ID, Authorization
  sessionList: true, // serve GET /sessions (default)
  maxStreamsPerSession: 8, // default
  maxBufferedBytes: 8 * 1024 * 1024, // default
};
```

<Warning>
CORS is on by default for every origin: a page of any origin can call a broker its visitor's browser can reach. Set `allowedOrigins`, or `cors: false`, for anything but a public demo.
</Warning>

- `maxStreamsPerSession` bounds the streams one session has open (the request that created it and the replay streams). A further one is answered with `429`.
- `maxBufferedBytes`: a reader that falls behind by more is disconnected. When it is the creator of the session, the session is cancelled.

### The Request Body of POST /sessions

```typescript
import type { CreateSessionRequest } from '@enclave-vm/broker';

const request: CreateSessionRequest = {
  code: 'return 1;',
  sessionId: 's_3f0e2f6e-1c1b-4c57-9a55-0a8b5a3d2c11', // optional
  config: {
    maxExecutionMs: 30_000, // lifetime of the session
    maxToolCalls: 10,
    heartbeatIntervalMs: 15_000,
  },
  filter: { mode: 'exclude', rules: [{ types: { types: ['heartbeat'] } }] },
};
```

The body is validated as a whole; a request that does not pass is answered with `400` and creates no session.

- `config` values are positive integers. `maxToolCalls` and `maxExecutionMs` cannot exceed the broker's limits (a larger value is lowered to them), and `heartbeatIntervalMs` is kept between 1 second and 5 minutes.
- `sessionId` is `s_` followed by 1 to 128 characters of `A-Z a-z 0-9 . _ : ~ -`. An id in use is answered with `409`.
- `filter` has bounds: 16 rules, 32 patterns, 256 characters per pattern.
- `encryption: { mode: 'required' }` is refused: the broker does not encrypt sessions.

### Answers

| Status | Code | When |
|--------|------|------|
| 400 | `INVALID_REQUEST`, `INVALID_FILTER`, `ENCRYPTION_NOT_SUPPORTED` | The request did not pass validation |
| 401 | `UNAUTHORIZED` | `identify` gave no caller |
| 404 | `NOT_FOUND` | No such session for this caller |
| 409 | `SESSION_EXISTS` | The session id is in use |
| 410 | `EVENTS_GONE` | A replay would start below the kept events |
| 429 | `TOO_MANY_STREAMS` | The session has `maxStreamsPerSession` streams open |
| 503 | `MAX_SESSIONS_REACHED` | `sessions.maxSessions` sessions are registered |
| 500 | `SESSION_CREATE_ERROR` | The session could not be created |

An error answer is `{ code, message }` with a fixed message.

## Event Filtering

Filter which events are sent to a client.

### Type-Based Filtering

```typescript
import { createEventFilter, createTypeFilter } from '@enclave-vm/broker';

// Do not send heartbeats and tool progress
const filter = createEventFilter({
  config: createTypeFilter('exclude', ['heartbeat', 'tool_progress']),
});

session.onEvent((event) => {
  if (filter.shouldSend(event)) sendToClient(event);
});
```

### Content-Based Filtering

```typescript
import { createEventFilter } from '@enclave-vm/broker';

const filter = createEventFilter({
  config: {
    mode: 'include',
    rules: [
      {
        types: { types: ['tool_call'] },
        content: {
          patterns: [
            { type: 'prefix', pattern: 'users_', field: 'payload.toolName' },
            { type: 'glob', pattern: 'report-*', field: 'payload.toolName' },
            { type: 'regex', pattern: '^(get|list)', field: 'payload.toolName', caseInsensitive: true },
          ],
          match: 'any',
        },
      },
    ],
    regexTimeoutMs: 100,
  },
});
```

A rule matches when its type filter and its content filter both match; a filter matches when one of its rules does. Without `field`, a pattern is matched against the payload as JSON text.

- Evaluating one event takes a bounded time: regular expressions and globs run under `regexTimeoutMs` (100 ms by default). The `budgetMs` option of `createEventFilter` bounds all evaluations of one filter together.
- An event the filter could not evaluate (a pattern that does not compile, an evaluation that ran out of time) is not sent, in either mode.
- In exclude mode a glob is matched as text: `*` also matches `/` and a leading dot. In include mode a glob follows path rules.
- A filter that arrives in a request gets at most 100 ms per event and 500 ms per stream, and its globs are matched without brace and extglob expansion.

### Always-Allowed Events

`session_init` and `final` are sent whatever the filter says, unless the configuration sets its own `alwaysAllow` list.

<Warning>
A filter is a convenience for the client, not a confidentiality control. Data that a client must not see has to stay out of the events: out of tool arguments and out of the result of the script.
</Warning>

## Tools from OpenAPI

```typescript
const source = broker.openapi({
  name: 'users',
  url: 'https://api.example.com/openapi.json',
  baseUrl: 'https://api.example.com',
  auth: { type: 'bearer', token: process.env.API_TOKEN! },
  intervalMs: 60_000,
  loaderOptions: { includeOperations: ['listUsers', 'getUser'] },
});

source.on('error', (error) => console.error('users API:', error.message));
source.on('toolsUpdated', ({ added, removed }) => console.log({ added, removed }));

await source.start(); // loads the specification, registers users_listUsers, users_getUser, and polls
source.getStats(); // { toolCount, lastUpdate, specHash, pollHealth, lastError? }
```

- A failure while polling is reported with the `error` event when it has a listener, and in `getStats()` either way. The tools of the last specification that was applied stay registered; tools are replaced in one step, and a source never replaces a tool it does not manage.
- A path parameter fills its own segment of the path. A value that would leave the segment empty or turn it into `.` or `..` fails the call.
- `auth` and `loaderOptions.headers` go to the origin of `baseUrl` only: not to a specification on another origin (the source's `headers` are for the specification host), and not along a redirect to another origin. A header parameter of the specification cannot replace them.
- Upstream responses are read up to `loaderOptions.maxResponseBytes` (10 MB by default), specifications up to `maxSpecBytes` (32 MB), and fetching a specification is bounded by `fetchTimeoutMs`.

Generate tools only for the operations a script may call: a script decides their arguments.
