This page documents all configuration options for @enclave-vm/core.

## Quick Example

```ts
import { Enclave } from '@enclave-vm/core';

const enclave = new Enclave({
  // Security level preset
  securityLevel: 'SECURE',

  // Core limits
  timeout: 10000,
  maxToolCalls: 50,
  maxIterations: 5000,

  // Tool handler
  toolHandler: async (name, args) => {
    return executeToolSafely(name, args);
  },

  // Additional options
  globals: { context: { userId: 'user-123' } },
  validate: true,
  transform: true,
});
```

## Core Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `securityLevel` | string | `'STANDARD'` | Preset: `STRICT`, `SECURE`, `STANDARD`, `PERMISSIVE` |
| `timeout` | number | 30000 | Maximum execution time in milliseconds. Script code is stopped at the deadline, also after an `await` (it checks the clock at every function entry and loop iteration). A tool call in progress when it passes is not cut off; the script's next tool call then fails with `Execution aborted` (same in `@enclave-vm/browser`). How long that call may still take is `toolCallGraceMs`. A script that is only waiting for something of its own when the deadline passes (a thenable that never calls back) is ended with the timeout error |
| `toolCallGraceMs` | number | same as `timeout` | How long, after `timeout` has passed, a tool call (or an async function from `globals`) that was in progress may still take to deliver its result. Then the execution ends with the timeout error and `error.data.pendingHostCalls` says how many calls were left running. `0` ends every execution at the deadline; `Infinity` waits for the handler however long it takes (the behaviour up to 2.18). Not used by the `worker_threads` adapter |
| `maxToolCalls` | number | 100 | Maximum tool calls per execution |
| `maxIterations` | number | 10000 | Maximum loop iterations (prevents infinite loops) |
| `toolHandler` | function | - | Async function that handles `callTool()` invocations |
| `toolNamespaces` | object | - | Expose tools as `ns.method(args)`: `{ mail: ['list', 'send'] }` or `{ users: { get: 'users:get' } }`. Each call is a `callTool()` call (see [Tool System](/enclave/core-libraries/enclave-vm/tool-system#tool-namespaces)) |
| `globals` | object | - | Additional globals available in script context |
| `allowFunctionsInGlobals` | boolean | varies | Allow functions in `globals`. Calls into them are gated: abort check, `maxGlobalFunctionCalls`, the double VM rate limit, and a sanitized copy of the result |
| `maxGlobalFunctionCalls` | number | 10 × `maxToolCalls` | Maximum calls into functions from `globals` per execution |
| `validate` | boolean | true | Validate code with ast-guard before execution |
| `transform` | boolean | true | Transform code before execution |
| `realmGlobals` | string | varies | Which standard globals exist in the script's realm. `'allowlist'`: only the names the validator allows (the default with the `agentscript` or `babel` preset while `validate` is on); every other global, including `Function`, `globalThis`, `Proxy`, `Reflect`, `Symbol`, `Promise` and `RegExp`, is removed and regular expressions cannot run. `'security-level'`: only the dangerous globals listed for the security level are removed (the default otherwise) |

Scripts run in strict mode at every security level: `this` is `undefined` outside a method call, an assignment to an undeclared name is an error, and a write that cannot happen (over a built-in method, or to a frozen object) throws a `TypeError` instead of being ignored.

## Console

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `consoleHandler` | `(level, message) => void` | - | Receive the script's `console.log/info/warn/error/debug` calls instead of the host console; allows `console` at every security level |
| `maxConsoleOutputBytes` | number | 1MB | Maximum total console output in bytes |
| `maxConsoleCalls` | number | 1000 | Maximum number of console calls |

Without a `consoleHandler`, `console` is allowed only at `PERMISSIVE` and writes to the host process console. With one, scripts may use `console` at every security level and each call reaches the handler instead:

```ts
const enclave = new Enclave({
  securityLevel: 'STRICT',
  consoleHandler: (level, message) => logger[level](message),
});

await enclave.run(`console.info('users', { count: 2 }); return 1;`);
// logger.info('users {"count":2}')
```

- `level` is `'log' | 'info' | 'warn' | 'error' | 'debug'` (`ConsoleLevel`); `message` is the formatted line: arguments joined by spaces, objects JSON-serialized.
- `maxConsoleCalls` and `maxConsoleOutputBytes` are checked before the handler runs. Past a limit, the script's call throws and the handler is not called.
- The handler's return value is ignored, and anything it throws or rejects with is swallowed: the script sees neither.
- The script's `console` is a frozen, null-prototype object built inside the sandbox. It holds no reference the script can reach to the handler or to any host object.
- Supported by the double VM (default), the `vm` adapter and the `worker_threads` adapter. A [custom sandbox adapter](#custom-sandbox-adapter) receives the handler as `context.consoleHandler`; the built-in `InterpreterAdapter` passes it one line of text per call and applies the same two limits, like the other adapters. `@enclave-vm/browser` has its own options and is unchanged.
- A `consoleHandler` cannot be combined with a `console` entry in `globals` (the constructor throws a `TypeError`).

## Memory Tracking

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `memoryLimit` | number | - | Memory limit in bytes (enables tracking) |

```ts
const enclave = new Enclave({
  memoryLimit: 32 * 1024 * 1024, // 32MB
});

const result = await enclave.run(code);
console.log('Peak memory:', result.stats.memoryUsage);
```

## Reference Sidecar

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `sidecar.enabled` | boolean | false | Enable sidecar for large data handling |
| `sidecar.maxTotalSize` | number | 10MB | Maximum total size of stored references |
| `sidecar.maxReferenceSize` | number | 1MB | Maximum size of a single reference |
| `sidecar.extractionThreshold` | number | 1024 | Minimum string size to extract |
| `sidecar.allowComposites` | boolean | false | Allow string concatenation with references |

```ts
const enclave = new Enclave({
  sidecar: {
    enabled: true,
    extractionThreshold: 1024,
    maxTotalSize: 50 * 1024 * 1024,
    allowComposites: false,
  },
});
```

## Double VM Layer

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `doubleVm.enabled` | boolean | true | Enable nested VM isolation |
| `doubleVm.parentTimeoutBuffer` | number | 1000 | Extra timeout for parent VM (ms) |
| `doubleVm.parentValidation.validateOperationNames` | boolean | true | Validate tool names |
| `doubleVm.parentValidation.allowedOperationPattern` | RegExp | - | Whitelist pattern for tool names |
| `doubleVm.parentValidation.blockedOperationPatterns` | RegExp[] | - | Blacklist patterns |
| `doubleVm.parentValidation.maxOperationsPerSecond` | number | 100 | Rate limiting |
| `doubleVm.parentValidation.blockSuspiciousSequences` | boolean | true | Detect attack patterns |
| `doubleVm.parentValidation.suspiciousPatterns` | array | - | Custom detection patterns |

```ts
const enclave = new Enclave({
  doubleVm: {
    enabled: true,
    parentValidation: {
      validateOperationNames: true,
      blockedOperationPatterns: [/^admin:/i],
      maxOperationsPerSecond: 50,
    },
  },
});
```

## Worker Pool Adapter

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `adapter` | string | `'vm'` | Where the sandbox runs: `vm` (in this process) or `worker_threads` (in a pool of worker threads). In both cases the script runs in the double VM, or in a single VM with `doubleVm: { enabled: false }` |
| `workerPoolConfig.minWorkers` | number | 2 | Minimum workers to keep warm |
| `workerPoolConfig.maxWorkers` | number | 8 | Maximum concurrent workers |
| `workerPoolConfig.memoryLimitPerWorker` | number | 256MB | Heap limit per worker, enforced by the engine; a worker that exceeds it is terminated and replaced |
| `workerPoolConfig.maxExecutionsPerWorker` | number | 1000 | Executions before worker recycle |
| `workerPoolConfig.maxQueueSize` | number | 100 | Maximum pending executions |
| `workerPoolConfig.maxMessagesPerSecond` | number | 1000 | Message flood protection |

```ts
const enclave = new Enclave({
  adapter: 'worker_threads',
  workerPoolConfig: {
    minWorkers: 2,
    maxWorkers: 16,
    memoryLimitPerWorker: 256 * 1024 * 1024,
  },
});
```

## Custom Sandbox Adapter

`@enclave-vm/core` runs scripts with `node:vm`. Where that is not available (a browser worker, an edge runtime), `run()` fails with `@enclave-vm/core needs node:vm, ...`; pass a `sandboxAdapter` to run scripts another way. It replaces the double VM and the `adapter` option.

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `sandboxAdapter` | `SandboxAdapter` | - | Object with `execute(code, context)` and `dispose()` that runs the validated, transformed script |

```ts
import { Enclave, InterpreterAdapter } from '@enclave-vm/core';

const enclave = new Enclave({ sandboxAdapter: new InterpreterAdapter() });
```

The enclave still validates and transforms every script before calling `execute`, but isolation is then the adapter's job: it receives the `ExecutionContext` (limits, tool handler, stats, abort signal) and must enforce it. The caller owns the adapter: `enclave.dispose()` does not dispose it, so one adapter can serve several enclaves. In a browser, `@enclave-vm/browser` is usually the better fit.

### The Interpreter Adapter

`InterpreterAdapter` is a tree-walking interpreter for AgentScript with no dependency on `node:vm`, QuickJS or WASM, for runtimes that have none of them. It runs the language the validator accepts, and a conformance suite compares it with the default sandbox script by script. Tool calls go through the same host bridge as in the other adapters (JSON both ways, the tool-call limit, sanitized arguments and results), and the returned value is copied into plain data.

It differs from the VM adapters in what isolates a script. There is one realm: the script works on ordinary objects of the host, and the interpreter decides, operation by operation, what it may do with them. So:

- The standard globals are frozen stand-ins with a fixed set of members (`Object.keys` exists, `Object.getPrototypeOf` does not), and nothing but data the script created can be changed.
- Calls are awaited as they are made: a function of the script cannot run in the background.
- Built-ins that would call a function of the script themselves are refused where the interpreter cannot wait for it (`JSON.parse` with a reviver, `Array.from` with a mapping function, `replace` with a function).
- Regular expressions, classes, generators and labels are not available.
- Custom `globals` must be JSON data; they are given to the script as frozen copies.

| Option | Default | Description |
|--------|---------|-------------|
| `maxSteps` | `5000000` | Evaluated nodes before the execution is ended (bounds loops) |
| `maxCallDepth` | `256` | Nested calls of script functions |
| `maxAllocationBytes` | `67108864` | What a script may allocate, as the interpreter estimates it; the execution's `memoryLimit` applies when it is lower |

## Execution Result

The `run()` method returns:

```ts
interface ExecutionResult<T> {
  success: boolean;
  value?: T;              // Result value (if success)
  error?: {
    name: string;
    message: string;
    code: string;         // Error code (see below)
    stack?: string;
    data?: unknown;       // Additional error context
  };
  stats: {
    duration: number;      // Execution time (ms)
    toolCallCount: number; // Tool calls made
    iterationCount: number; // Loop iterations
    memoryUsage?: number;  // Peak memory (if tracked)
    sidecar?: {
      referencesCreated: number;
      totalBytesStored: number;
      resolutionCount: number;
    };
  };
}
```

## Error Codes

| Code | Description |
|------|-------------|
| `VALIDATION_ERROR` | AST validation failed |
| `EXECUTION_ERROR` | Runtime error in script |
| `TIMEOUT` | Execution exceeded timeout |
| `TOOL_ERROR` | Tool call failed |
| `MAX_TOOL_CALLS` | Tool call limit exceeded |
| `MAX_ITERATIONS` | Loop iteration limit exceeded |
| `MEMORY_LIMIT_EXCEEDED` | Memory limit exceeded |
| `SCORING_BLOCKED` | Blocked by scoring gate |
| `SIDECAR_SIZE_EXCEEDED` | Sidecar storage limit exceeded |
| `SIDECAR_COMPOSITE_BLOCKED` | String concatenation blocked |
