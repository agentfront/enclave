# Security test catalog

Every security property of the sandbox has a category, and every category has tests. This file is the index: which layer owns a property, the category code its tests carry, and where they live. Keep it in step with the tests; the rules at the end are what keep the suite meaningful.

## Running the tests

```bash
git submodule update --init security-tests   # once; needs access to the private repository

yarn test                       # every Jest suite: the public ones and the security specs
npx nx test ast                 # static layer
npx nx test core                # runtime, bridge, limits
npx nx test-e2e browser         # @enclave-vm/browser in Chromium (Playwright; `npx playwright install chromium` once)
yarn test:security              # the security tests alone: case suite, specs of every library, browser specs
yarn test-script --suite        # AgentScript case files, run the way the CodeCall plugin runs them
yarn test-script --suite security-tests/test-script/known-gaps   # invariants that are not delivered yet
```

### Where the tests are

The security tests are not in this repository. They live in a private one (`agentfront/enclave-security-tests`), included here as the git submodule `security-tests`, so that a script written to leave the sandbox is not public: not before the fix it tests is released, and not afterwards as a collection of attempts.

| Folder of the submodule                                                        | What it holds                                                                 | Runs as part of                                         |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------- |
| `specs/ast`, `specs/core`                                                      | The Jest suites of the tables below                                           | `npx nx test ast`, `npx nx test core`                   |
| `specs/browser`                                                                | Playwright specs of the boundary between the host page and its iframes        | `npx nx test-e2e browser` (project `chromium-security`) |
| `specs/broker`, `specs/client`, `specs/stream`, `specs/react`, `specs/runtime` | The Jest suites of the packages around the sandbox ("Network packages" below) | `npx nx test <library>`                                 |
| `test-script`                                                                  | The AgentScript case suite and its runner                                     | `yarn test-script --suite`                              |

The Jest and Playwright configurations of the libraries add the submodule's folder when it exists, so with the submodule checked out the commands above run everything, as they did when the suites were in `libs/`. Without it they run the public suites only, and `yarn test:security` and `yarn test-script` say that the submodule is missing and exit with 2.

What stays in this repository are the functional suites, which hold no attempt: the rule, preset and transform unit tests of `libs/ast` (`rules`, `presets`, `agentscript`, `transformer`, `agentscript-transformer`, `transforms`, `validator`, `tool-namespaces`, `scope-analysis`, `static-call-target`, `pre-scanner`, `redos-entry`, `infinite-loop.rule`), and in `libs/core` the suites of the public API and the adapters (`enclave`, `enclave.security-levels`, `enclave.console-handler`, `enclave.result-sanitization`, `enclave.error-stack`, `enclave.timeout-tool-calls`, `enclave.tool-gate`, `enclave.sidecar`, `sidecar/reference-resolver`, `globals-validator`, `safe-runtime`, `tool-bridge`, `memory-limit`, `interpreter-conformance`, `interpreter-transform-integration`, `vm-adapter`, `worker-pool-adapter`, `worker-pool-components`, the Babel, scoring and session suites, and the benchmarks under `perf/`). Every other suite named in this file is in `security-tests/specs/<library>`. Where a functional suite had security tests in it, they are in a suite of the same name ending in `.security`.

### CI

CI runs the security tests for every push to this repository, which includes the branches of its pull requests (job "Security tests" in `.github/workflows/push.yml`). The job checks the submodule out at the commit this repository pins, with the secret `SECURITY_TESTS_TOKEN`, a token that can only read that repository. Pushes from forks and from Dependabot do not have the secret and do not run the job; without the secret the job fails rather than skipping.

The logs of that CI are public, so the job runs the tests with `--summary` (`scripts/security-tests.mjs`): every part runs as a child process whose output is discarded, and what is printed is a count per part. No test name, no script, no value and no path reaches the log, and the job uploads no report. A failure is reproduced locally with `yarn test:security`. The other jobs (Test, Browser E2E) do not check the submodule out, so their logs and reports hold the public suites only.

`yarn test-script` puts a random canary in the host's environment and snapshots the host's built-in prototypes around every case. A case that leaks the canary or changes the host is reported as `BYPASS` whatever it expected (exit code 3).

## How the tests are organised

A script passes through five layers, and the host process around them is a sixth concern. Each layer has to hold **on its own**: a test of a runtime property that goes through validation only proves the validator refused the script.

| Layer           | What it guarantees                                                                                   | Package     |
| --------------- | ---------------------------------------------------------------------------------------------------- | ----------- |
| 1. Static       | A script is made only of allowed syntax, names and property keys                                     | `libs/ast`  |
| 2. Realm        | The realm a script runs in holds nothing beyond its allowed globals                                  | `libs/core` |
| 3. Bridge       | Nothing crosses from the host or the parent VM into a script unwrapped                               | `libs/core` |
| 4. Host         | What a script returns or sends to a tool is plain, size-bounded data                                 | `libs/core` |
| 5. Limits       | Iteration, memory, time, tool-call and output limits cannot be switched off                          | `libs/core` |
| 6. Host process | Running scripts do not crash the host (one open invariant, below), and a worker is not trusted by it | `libs/core` |

The packages around the sandbox (`broker`, `client`, `stream`, `react`, `runtime`) are not a layer of it: a script never runs in them. Their invariants are about the callers of a server and the peer of a connection, and have a section of their own ("Network packages").

Test names carry a category code, `ATK-<CODE>-NN`, with the weakness class in the suite title: `ATK-MERR: Membrane Error Laundering (CWE-209)`.

The interpreter adapter has one realm, so the layers above do not apply to it as written; it has its own three suites. `interpreter-security` (ATK-INTERP-01 to 29, and 32 to 36) pins what its rules deliver: host built-ins are read-only, the standard globals are stand-ins without reflection, a script catches copies of errors and cannot catch a limit, allocation is bounded, a bound on what one built-in call may produce holds however the call is written (also for a built-in used as a callback) and a built-in method only works on the kind of value it belongs to, a dropped rejection does not reach the process, tool data and results cross as plain data, recursion ends at the call depth through every way a function can be called while the calls in progress are bounded as a whole, and the prototypes every object shares are never data of a script. `interpreter-limits` (ATK-INTERP-37 to 47) pins what happens where something acts for a script, and what one step may cost: a promise of a runtime helper that nobody holds does not reach the process; data of a script holds no function under a name the engine calls by itself, so a conversion, a serialization or an `await` runs nothing for a script, and a tool namespace has no such member either; a built-in gets the argument its bound was checked with; the built-ins a script can call are the listed ones, each on its own kind of value, and an engine built-in takes a function only as data; a BigInt is bounded in size and counted against both budgets; the timeout bounds a script that computes, the work of a built-in counts as steps in proportion to what it reads, and a search whose cost is the product of two lengths is made in pieces; nothing reaches the host once the execution has returned; the allocation budget cannot be caught wherever it is charged; a text made by `+` is charged in full, and one that only grows in a variable or through `reduce` for what is appended; and the bounds on what one call may produce have no gaps. ATK-INTERP-37 also starts a second Node.js process against the built packages. `interpreter-conformance` (public) runs a corpus of AgentScript through the default sandbox and through the interpreter and requires the same outcome; `interpreter-conformance.security` (ATK-INTERP-30, -31) does the same for scripts that run into a limit or name a blocked key. `interpreter/interpreter` and `interpreter-transform-integration.security` hold the older checks of the same rules.

## Open invariants

Six. Two are tracked by a test that is expected to fail (ATK-STACK-08, ATK-BTIME-05); the others have no test of their own, for the reason each entry gives:

- **ATK-WORKER, layer 6: the host process survives whatever a worker allocates.** A worker thread shares the process. When a worker reaches its heap limit, Node.js ends the worker and lets the engine finish what it is doing; an allocation burst that outruns that is a fatal out-of-memory error for the whole process. That is a property of worker threads, seen with plain JavaScript in a worker and no sandbox. Inside the sandbox the measured load ended only its worker on an idle machine, but under load it aborted the process in a few runs of a hundred as long as the worker had the engine's default young generation. The pool now bounds the young generation (ATK-WORKER-45), and the same load has not aborted a process since (0 of 480 at 12 in parallel). What stays open is an allocation the engine cannot finish within what Node.js allows it. By default the sandbox's own `memoryLimit` stops a script long before the worker's limit. ATK-WORKER-14 and ATK-WORKER-34 run such a load and assert what the pool does when the engine ends the worker; ATK-WORKER-34 repeats a run that the engine aborted, and three in a row fail it. There is no `it.failing` test and no `known-gaps` case for it: the failing outcome is the death of the test process, and a script written to produce it would be an attack on the host, not a regression test. A host that needs this property runs the enclave in a child process or a container with a memory limit of the operating system (`libs/core/README.md`, "The Worker Heap Limit").

- **ATK-STACK, layer 6: a script cannot make the host process write to its stderr.** When a promise is rejected while the stack is full, Node.js cannot run its own bookkeeping for the rejection and prints a block (`Exception in PromiseRejectCallback`, with the source line that was executing) straight to the process's stderr, from native code. A script can produce such blocks at a few megabytes per second for as long as it runs, and the printed line is a line of the script. Nothing in JavaScript can intercept the write, in a worker thread either; plain Node.js behaves the same without a sandbox. The other consequences of a rejection at a full stack are covered (ATK-REJECT, ATK-STACK-04). A host for which stderr matters gives it a size limit, does not parse it for decisions, or runs the sandbox in a child process whose stderr it controls. Tracked by `it.failing` (ATK-STACK-08). It has no `known-gaps` case: a case is judged by what its script returns, and this outcome is what the host process prints.

- **ATK-TIME and ATK-MEMACC, layer 5: in process, the time and memory limits are the enclave's own accounting, not the engine's.** The deadline is checked between the steps of a script's own code, and `memoryLimit` counts the operations that make text and arrays grow. One call into a built-in is finished by the engine before the next check, so `timeout` does not bound it: what bounds an array built-in is the length it works through, which is at most what an array may have under `memoryLimit` (ATK-TIME, ATK-MEMACC), and with `memoryLimit: 0` nothing does. A copy is not charged, and objects, Maps and Sets are not counted. The accounting cannot be switched off or reset from inside (ATK-LCTR, ATK-MEMACC, ATK-TIME), but it is an estimate. A host that needs the engine's own bounds runs the enclave with the worker pool adapter, where a worker has a heap limit and is ended at the deadline (ATK-WORKER), or in a child process or container with limits of the operating system. The same holds for a server that runs enclaves for its callers on its own thread, such as the broker. There is no failing test for it: the limits that exist are pinned by the categories above, and what is missing is a property of running in the host's thread.

- **ATK-STACK, layer 6, Node.js 22 only: an application with promise hooks active is not protected from an error raised inside its own hook while a script runs.** On Node.js 22 an application that calls `run()` inside `AsyncLocalStorage.run()`, or that has enabled an `async_hooks` hook, has the engine call that hook for the promises a script creates, and Node.js reports an error raised inside a hook as uncaught. Node.js 24 keeps the async context without the hook and is not affected; plain Node.js 22 behaves the same without a sandbox. A host on Node.js 22 with such hooks runs the enclave with the worker pool adapter or in a child process, or moves to Node.js 24. It has no test, for the reason given for ATK-WORKER: the failing outcome is the death of the test process.

- **ATK-BTIME, browser: a script that computes without yielding ends at the timeout.** The sandbox frames share a thread, and in some browsers they share it with the host page: no timer fires while a script holds it. Where the frames run in another process than the page, the host page ends the run at its hard stop; where they do not, `run()` returns when the script has finished. Tracked by ATK-BTIME-05, which is expected to fail where the frames share the page's process (the headless shell of the test browser) and passes in the full browser.

- **Browser, layers 2 and 5: with the static layer off, the inner frame's own state is the script's.** The browser enclave runs a script in a document, next to the code that sets the sandbox up. With `validate: false`, or with a preset that lets a script name the frame's window, the limits and counters that live in that frame can be reached by the script. What does not depend on the validator there: the frames open no connection and run no other script (ATK-BNET), and the host page checks every message and enforces the tool-call and console limits itself (ATK-IFRAME). The browser enclave is for validated AgentScript; it has no test because the documentation of the package states it as the boundary of what the frame can enforce.

When an invariant is known not to hold, it is listed here with its code, and tracked so it cannot be forgotten: in the `OPEN` set of its Jest suite (the test runs with `it.failing` and reports itself the moment it starts passing) and, where the outcome can be stated as the result of a script, as a case under `security-tests/test-script/known-gaps/`.

## Rules for changing the sandbox

1. **A fix comes with its test.** Write the test first and watch it fail against the unfixed code, then fix. A test that passes before the fix is not testing the fix.
2. **Test the layer that owns the property, with the other layers off.** Use `validate: false` (and `transform: false` for pre-wrapped code) for a runtime property, and assert the validator's issue code for a static one. Then add a case file for the full pipeline.
3. **Put the test in its category.** A new class of weakness gets a new `ATK-<CODE>`, a row in this file and, where it can be expressed under validation, a case folder.
4. **Prefer invariants to exploits.** A script that reports `typeof`, a frozen flag or a count, checked against what a secure runtime answers, keeps working as a regression test after the particular exploit path is closed. Where the effect is on the host, check the host object the test passed in.
5. **Cover the breadth, not the one spelling that was reported.** If a rule refuses `a.b`, the test lists `a?.b`, `a['b']`, ``a[`b`]``, `a[['b']]`, the assignment-target and destructuring forms, and the aliases that reach the same thing.
6. **A test that holds an attempt goes to the submodule.** A script written to escape, to bypass a rule or to exhaust a limit belongs in `security-tests/` (`specs/<library>` for Jest and Playwright, `test-script/cases` for the full pipeline), never in `libs/`. What `libs/` keeps are functional tests: what a rule flags, what an option does. Commit there first, then move the submodule entry in the same pull request as the change it tests (`git add security-tests`). Nothing from the submodule is quoted in a public place: refer to a test by its code and the invariant in this file.
7. **An invariant that does not hold yet is still a test.** In Jest, list its id in the suite's `OPEN` set so it runs with `it.failing` and reports itself the moment it starts passing; in the case suite, put it under `known-gaps`. When it is fixed, remove it from `OPEN` or move it into `cases/<category>/`, and delete its row above. Never add an id to `OPEN` to silence a test that used to pass.
